Las 3 Identidades

El concepto central que hay que tener claro para entender todo. Hay 3 cosas distintas que pueden confundirse:

IdentidadQué esTablaCambia?
Persona Ser humano real (Duilio, Anggie) — Casi nunca
Cuenta Credenciales (DNI + clave) users + members Una vez, persiste
Dispositivo Cada navegador en cada equipo devices Constantemente
Regla clave: Una persona tiene UNA cuenta y MUCHOS dispositivos.

Ejemplo concreto: Duilio

  • 1 persona: tú
  • 1 cuenta: user_id=X (DNI 05393776, rol SOTE)
  • N dispositivos:
    • Chrome PC oficina
    • Chrome PC casa
    • Chrome celular Android
    • Safari iPad

Cada vez que abres la PWA en un navegador nuevo, se crea un device NUEVO. El sistema NO sabe que es la misma persona; sabe que el mismo user_id tiene 4 devices asociados.

Flujo Push completo

De principio a fin, qué pasa desde que el usuario abre el sitio hasta que recibe push:

Paso 1 — La cuenta YA existe (pre-requisito) users → members → (rol en CCPL) Paso 2 — Login Decano escribe "DECANO" + clave ↓ Backend: UPPER(input) → buscar en users + validar Argon2 ↓ Sesión iniciada (cookie en navegador) Paso 3 — Suscripción VAPID (clave!) Toca botón "Activar notificaciones" ↓ JS: Notification.requestPermission() ↓ SO: popup "¿Permitir notificaciones?" ↓ Acepta ↓ JS: pushManager.subscribe({applicationServerKey: VAPID_PUBLIC_KEY}) ↓ Google FCM / Apple APNS: genera endpoint único ↓ JS: POST /api/comunicados/push/registrar ↓ Backend: INSERT INTO devices (member_id, endpoint, p256dh, auth) Paso 4 — Envío de push Anggie cobra ↓ Hook 6.1 → notif_service.disparar_evento("pago_caja", ...) ↓ SELECT user_ids elegibles (notif_role_categoria + notif_user_categoria) ↓ Para cada user → buscar devices activos ↓ pywebpush.webpush(...) → cifra con p256dh/auth ↓ Google FCM entrega al SO del Decano ↓ Service Worker descifra y muestra notificación

Glosario — VAPID

VAPID — Voluntary Application Server Identification Protocolo para que tu servidor pueda enviar push notifications a navegadores sin pasar por servicios de terceros como Firebase. Usas un par de claves: pública (la conoce el navegador) y privada (la guarda tu servidor). Las claves están en Railway env vars: VAPID_PUBLIC_KEY, VAPID_PRIVATE_KEY, VAPID_CLAIMS_EMAIL.

PWA

PWA — Progressive Web App Aplicación web que se comporta como app nativa: se "instala" en el celular, funciona offline parcialmente, recibe push notifications. CCPL ES una PWA. El usuario la instala desde el navegador con "Agregar a pantalla de inicio".

Service Worker

Service Worker Código JavaScript que corre en segundo plano en el navegador, INCLUSO si la PWA está cerrada. Es lo que recibe los push y muestra la notificación. En CCPL es el archivo sw.js. Se registra una vez y queda "activo" para siempre (mientras el usuario no borre datos).

WebSocket

WebSocket Conexión bidireccional persistente entre navegador y servidor. Mientras la página está abierta, se mantiene conectada y pueden mandarse mensajes en tiempo real (sin que el cliente pregunte cada N segundos).

Diferencia con Push: WebSocket requiere que la página esté abierta. Push funciona incluso con la PWA cerrada.

CCPL usa ambos: WebSocket para chat en vivo (/ws/alerta), Push para notificaciones importantes.

Polling

Polling El cliente le pregunta al servidor cada N segundos "¿hay novedades?". Es el método más viejo. Ineficiente, gasta batería y datos. CCPL evita polling cuando puede.

FOMO

FOMO — Fear Of Missing Out En CCPL v2 (reinterpretado): avisos automáticos del sistema basados en reglas (vence en 5 días, asamblea mañana). Antes eran mensajes motivacionales aleatorios. Ahora son útiles.

Tabla: fomo_avisos. Cada fila es un aviso a una persona específica.

Diagnóstico — ¿Por qué no llega push?

Decision tree para depurar:

1. ¿El user_id está en notif_log? 
SELECT evento_tipo, resultado, sent_at::timestamp 
FROM notif_log 
WHERE user_id = ?
ORDER BY sent_at DESC LIMIT 5;
  • SIN registro El user NO es destinatario. Verificar mapeo role→categoria.
  • resultado='silenciado_por_config' El usuario apagó esa categoría en /notificaciones.
  • resultado='sin_device' No tiene PWA activada. Salto al paso 2.
  • resultado='error' Algo falló al enviar. Ver error_detalle.
  • resultado='enviado' El push se mandó. Salto al paso 3.
2. ¿Tiene devices activos? 
SELECT id, push_endpoint, is_active, created_at::timestamp
FROM devices
WHERE member_id = (
  SELECT id FROM members WHERE user_id = ?
);
  • Sin filas Nunca aceptó push. Debe entrar y aceptar.
  • is_active=false Suscripción expirada. Reactivar.
  • is_active=true Salto al paso 3.
3. ¿El navegador puede recibir?

En el celular del usuario, verificar:

  • ¿El navegador tiene permisos de notificaciones para ccploreto.org.pe?
  • ¿El SO no está en modo silencio / no molestar?
  • ¿La PWA está instalada (no solo abierta en navegador)?

Error 410 Gone

Significa: el endpoint del device ya no existe. El navegador lo descartó por: usuario borró datos, desinstaló PWA, revocó permiso, o expiró por inactividad.

Solución: el sistema debería marcar el device como is_active=false al recibir 410. Limpieza pendiente en backlog.

Query — Devices activos

Cuántas personas tienen push

SELECT COUNT(DISTINCT member_id) AS personas_con_push,
       COUNT(*) AS devices_totales
FROM devices 
WHERE is_active = TRUE;

Top 10 con más devices

SELECT u.public_id, u.name, COUNT(d.id) AS devices_activos
FROM members m
JOIN users u ON u.id = m.user_id
JOIN devices d ON d.member_id = m.id AND d.is_active = TRUE
GROUP BY m.user_id, u.public_id, u.name
ORDER BY devices_activos DESC 
LIMIT 10;

Devices expirados pendientes de limpiar

SELECT COUNT(*) FROM devices WHERE is_active = FALSE;

Query — Bitácora notif_log

Resumen últimos 7 días

SELECT resultado, COUNT(*) AS cantidad
FROM notif_log
WHERE sent_at > NOW() - INTERVAL '7 days'
GROUP BY resultado
ORDER BY cantidad DESC;

Tasa de entrega por evento

SELECT evento_tipo,
       COUNT(*) FILTER (WHERE resultado='enviado') AS enviados,
       COUNT(*) FILTER (WHERE resultado='sin_device') AS sin_device,
       ROUND(100.0 * COUNT(*) FILTER (WHERE resultado='enviado') / NULLIF(COUNT(*),0), 1) AS tasa_entrega
FROM notif_log
WHERE sent_at > NOW() - INTERVAL '7 days'
GROUP BY evento_tipo
ORDER BY tasa_entrega DESC;

Eventos por usuario (top 20)

SELECT u.name, COUNT(*) AS push_recibidos
FROM notif_log l
JOIN users u ON u.id = l.user_id
WHERE l.sent_at > NOW() - INTERVAL '7 days'
  AND l.resultado = 'enviado'
GROUP BY u.id, u.name
ORDER BY push_recibidos DESC
LIMIT 20;

Query — Colegiados sin member

SELECT 
  COUNT(*) FILTER (WHERE member_id IS NULL) AS sin_member,
  COUNT(*) FILTER (WHERE member_id IS NOT NULL) AS con_member,
  COUNT(*) AS total
FROM colegiados
WHERE organization_id = 1;

Lista de irregulares

SELECT codigo_matricula, apellidos_nombres, dni
FROM colegiados
WHERE organization_id = 1 AND member_id IS NULL
ORDER BY dni;

Query — Accesos al sistema

Top usuarios por sesiones esta semana

SELECT u.public_id, u.name, COUNT(*) AS sesiones
FROM access_logs a
JOIN users u ON u.id = a.user_id
WHERE a.created_at > NOW() - INTERVAL '7 days'
GROUP BY u.id, u.public_id, u.name
ORDER BY sesiones DESC 
LIMIT 20;

Colegiados que entran al sistema (¿adopción?)

SELECT 
  COUNT(DISTINCT m.user_id) AS colegiados_activos_semana,
  (SELECT COUNT(*) FROM colegiados WHERE organization_id=1 AND condicion='habil') AS colegiados_habiles_totales
FROM access_logs a
JOIN members m ON m.user_id = a.user_id  
WHERE m.organization_id = 1
  AND m.role IN ('colegiado','user')
  AND a.created_at > NOW() - INTERVAL '7 days';

Query — Configuración de categorías

Quiénes apagaron alguna categoría

SELECT u.name, nc.categoria, nc.modo, nc.activo
FROM notif_config nc
JOIN users u ON u.id = nc.user_id
WHERE nc.activo = FALSE OR nc.modo = 'silencioso'
ORDER BY u.name;

Distribución por modo de entrega

SELECT modo, COUNT(*) AS usuarios
FROM notif_config
WHERE activo = TRUE
GROUP BY modo
ORDER BY usuarios DESC;

Métricas — Adopción WebApp

Estas métricas son tu "as bajo la manga" para conversaciones con directivos. Demuestran tracción real.

Adopción de notificaciones

-- Penetración de push notifications
WITH stats AS (
  SELECT 
    (SELECT COUNT(DISTINCT m.id) 
     FROM members m JOIN devices d ON d.member_id=m.id 
     WHERE d.is_active=TRUE AND m.organization_id=1) AS con_push,
    (SELECT COUNT(*) FROM members WHERE organization_id=1 AND is_active=TRUE) AS total
)
SELECT con_push, total, 
       ROUND(100.0 * con_push / NULLIF(total,0), 1) AS pct_adopcion
FROM stats;

Curva de adopción semanal

SELECT 
  DATE_TRUNC('week', created_at)::date AS semana,
  COUNT(*) AS devices_nuevos,
  SUM(COUNT(*)) OVER (ORDER BY DATE_TRUNC('week', created_at)) AS acumulado
FROM devices
WHERE created_at > NOW() - INTERVAL '90 days'
GROUP BY 1 ORDER BY 1;

Métricas — Pagos web vs caja

SELECT 
  DATE_TRUNC('week', p.created_at)::date AS semana,
  COUNT(*) FILTER (WHERE p.payment_method='cash' OR p.notes LIKE '%CAJA%') AS pagos_caja,
  COUNT(*) FILTER (WHERE p.notes LIKE '%OPENPAY%' OR p.notes LIKE '%web%') AS pagos_web,
  SUM(p.amount) FILTER (WHERE p.notes LIKE '%CAJA%') AS monto_caja,
  SUM(p.amount) FILTER (WHERE p.notes LIKE '%OPENPAY%') AS monto_web
FROM payments p
WHERE p.created_at > NOW() - INTERVAL '60 days'
  AND p.organization_id = 1
GROUP BY 1 ORDER BY 1;

Métricas — Deuda y morosidad

Saldo total pendiente

SELECT 
  COUNT(*) AS deudas_pendientes,
  COUNT(DISTINCT colegiado_id) AS colegiados_morosos,
  SUM(balance) AS saldo_total
FROM debts
WHERE organization_id = 1 
  AND status = 'pending'
  AND balance > 0;

Morosidad por concepto

SELECT 
  cc.nombre AS concepto,
  COUNT(*) AS deudas,
  SUM(d.balance) AS saldo
FROM debts d
LEFT JOIN conceptos_cobro cc ON cc.id = d.concepto_cobro_id
WHERE d.organization_id = 1 
  AND d.status = 'pending'
GROUP BY cc.nombre
ORDER BY saldo DESC;

Fraccionamientos en riesgo

SELECT 
  COUNT(*) FILTER (WHERE estado = 'activo') AS activos,
  COUNT(*) FILTER (WHERE estado = 'perdido') AS perdidos,
  COUNT(*) FILTER (WHERE estado = 'completado') AS completados
FROM fraccionamientos
WHERE organization_id = 1;
